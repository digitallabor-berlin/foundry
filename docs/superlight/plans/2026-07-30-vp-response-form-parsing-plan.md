# Spec-Compliant `direct_post.jwt` Response Parsing — Implementation Plan

**Spec:** docs/superlight/specs/2026-07-30-vp-response-form-parsing-spec.md
**Branch:** superlight/2026-07-30-vp-response-form-parsing
**Executed with:** superlight Phase 4 (TDD, inline, no subagents by default)

**Goal:** `POST /vp/response/{id}` accepts the OpenID4VP `direct_post.jwt`
response shape — `application/x-www-form-urlencoded` with the JWE in a
`response` parameter — and rejects the previous raw-body shape.

**Architecture:** The handler stops consuming the raw body and instead parses it
with `serde_html_form` into a `VpResponseForm { response: String }`, mirroring
the existing `token_handler` precedent (`server.rs:342-364`). Everything
downstream of the `verify_vp_response` call is untouched. foundry's own debug
wallet and all integration-test call sites migrate to the conformant shape in
the same task, because they are the only two consumers of the old shape.

**Global Constraints** (copied verbatim from the spec):

- Verification gates: `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --check` — all three must pass clean.
- No `.unwrap()`, `.expect()`, `panic!()` or `unreachable!()` in request-handling paths (root `AGENTS.md` §4.1); permitted only under `#[cfg(test)]` and in `tests/`.
- `VerificationResult.verified` MUST remain `checks.iter().all(|c| c.passed)` (§4.2) — this change must not touch that computation.
- Structural/crypto errors → HTTP 400; policy failures → HTTP 200 with `verified: false`; status-fetch unavailability → HTTP 502 (§4.3).
- Endpoint changes MUST be reflected in `openapi-wallet.json` (§6).
- `#[utoipa::path]` attributes MUST reference schema types by **unqualified** name — a qualified path generates a dotted `$ref` that never resolves against `components.schemas` (regression fixed in commit `09b0bb0`).
- The form parameter name is exactly `response` (OpenID4VP 1.0 §8.3).
- Unknown form parameters MUST be ignored; never add `deny_unknown_fields`.
- No new workspace dependencies. `serde_html_form = "0.2"` is already a dependency of `crates/foundry` (`Cargo.toml:28`).
- Dependency layering is one-directional: `foundry-core` → format crates → engines → `foundry` → `foundry-wallet`. No upward or sideways edges.
- `openapi-wallet.json` is regenerated by running `serve`; the `foundry openapi` CLI subcommand writes the **admin** spec only.

## File Structure

- `crates/foundry/src/server.rs` — `VpResponseForm` struct; `post_response_handler` body parsing; `#[utoipa::path]` request-body annotation
- `crates/foundry/src/openapi.rs` — register `VpResponseForm` in `WalletApiDoc`'s `components(schemas(...))` (block at lines 50-64)
- `crates/foundry-wallet/src/actions/verification.rs` — post the conformant form body (line 175)
- `crates/foundry-wallet/src/http/mod.rs` — remove `post_text` (lines 113-127) once unused
- `crates/foundry/tests/wallet_verification.rs` — 9 call-site migrations + 4 new tests
- `crates/foundry/tests/e2e_full_flow.rs` — 1 call-site migration (line 446)
- `crates/foundry/tests/openapi_endpoints.rs` — content-type assertion for the request body
- `openapi-wallet.json` — regenerated artifact; `serve()` rewrites both specs on startup (`server.rs:730-744`)

### Why only two tasks

`crates/foundry-wallet/tests/verification.rs` calls `support::spawn_test_server()`
and lists `foundry` as a dev-dependency — it drives a **real in-process foundry
server**. Changing the server without simultaneously migrating the debug wallet
client would leave `cargo test --workspace` red across a commit. Server and
client are therefore one task by necessity, not by preference.

### Task 1: Parse the `direct_post.jwt` form body, and migrate both clients

**Files:**
- modify `crates/foundry/src/server.rs` (`post_response_handler` signature, `576-580`; new struct alongside it)
- modify `crates/foundry-wallet/src/actions/verification.rs` (`175`)
- modify `crates/foundry-wallet/src/http/mod.rs` (remove `post_text`, `113-127`)
- test `crates/foundry/tests/wallet_verification.rs` (migrate lines 298, 448, 466, 537, 670, 694, 791, 913, 1068; add 4 tests)
- test `crates/foundry/tests/e2e_full_flow.rs` (migrate line 446)

**Interfaces:**
- Produces: `VpResponseForm { response: String }` — private to `crates/foundry::server`. **`server.rs` has no `use serde::...` import; follow the existing convention at line 235 and derive fully qualified: `#[derive(Debug, serde::Deserialize)]`.** `utoipa::ToSchema` is deliberately *not* added here — that belongs to Task 2, because the derive is only meaningful once the type is registered in `components(schemas(...))`.
- Consumes: `serde_html_form::from_bytes` (already used at `server.rs:360`), `axum::body::Bytes`.
- Handler signature becomes `(State<AppState>, Path<String>, axum::body::Bytes)`; `&form.response` replaces `&encrypted_jwe_str` at the `verify_vp_response` call.
- Unchanged: the 404 / already-submitted / `verifier_wallet_error_response` paths, and the `save_verification_transaction` call that must still run after a verification attempt.

**Behaviors to test:**
- Conformant form body (`Content-Type: application/x-www-form-urlencoded`, body `response=<jwe>`) → 200, `verified: true`, four `CheckResult` records — happy path, and the regression test for the reported defect
- Raw JWE body (the previous shape) → 400 `invalid_request` — must be red first: today this returns 200
- Well-formed form body without a `response` parameter (e.g. `state=abc`) → 400 `invalid_request`, **asserting the parse-failure `error_description`, not merely the status** — a bare status assertion passes accidentally today via the decryption path
- `response=<jwe>&state=abc` → 200 — extra parameters tolerated, proving `deny_unknown_fields` was not introduced

**Notes:**
- No percent-encoding call is needed wallet-side: the JWE alphabet is base64url (`A–Z a–z 0–9 - _`) plus `.` separators, all RFC 3986 unreserved. Record that as a code comment, not a silent assumption. `serde_html_form` percent-decodes server-side regardless, so an encoding wallet also works.
- `post_text`'s only caller is `verification.rs:175`. It is `pub` in the `foundry_wallet` lib, so an unused copy will **not** trip `dead_code`; remove it deliberately rather than relying on the linter.
- The `#[utoipa::path]` annotation is knowingly left stale in this task (it still says `content = String`). Task 2 corrects it. The branch is not mergeable until both land.

### Task 2: Document the form request body in the wallet OpenAPI spec

**Files:**
- modify `crates/foundry/src/server.rs` (the `#[utoipa::path]` attribute at `570-575`; add `utoipa::ToSchema` to `VpResponseForm`)
- modify `crates/foundry/src/openapi.rs` (`components(schemas(...))`, lines 50-64)
- test `crates/foundry/tests/openapi_endpoints.rs`
- regenerate `openapi-wallet.json`

**Interfaces:**
- Consumes: `VpResponseForm` from Task 1 — must gain `#[derive(utoipa::ToSchema)]`.
- Produces: `request_body(content = VpResponseForm, content_type = "application/x-www-form-urlencoded", description = …)` on `post_response_handler`, and a `VpResponseForm` entry in `WalletApiDoc`'s schema list.
- **The attribute must name the type unqualified.** A qualified path emits a dotted `$ref` that never resolves — this is the exact `09b0bb0` regression, and `wallet_openapi_spec_all_refs_resolve` (`openapi_endpoints.rs:326`) is the test that catches it.
- `VpResponseForm` is `pub(crate)`; if `utoipa`'s generated schema code requires broader visibility, widen the type's visibility rather than qualifying the attribute path.

**Behaviors to test:**
- The generated wallet spec's `/vp/response/{id}` request body advertises `application/x-www-form-urlencoded` — happy path; this is the one new test in this task and must be red first
- Every `$ref` in the generated wallet spec resolves — already covered by the existing `wallet_openapi_spec_all_refs_resolve`; it must stay green, which is the guard against the dotted-`$ref` mistake

**Notes:**
- Regenerating `openapi-wallet.json` is a **build step, not a test**. No test currently compares the committed file against the generated spec — verified, none exists — so the regenerated file must be committed by hand and eyeballed in the diff. Do not claim test coverage for it.
- Regenerate via `serve` (`server.rs:730-744` writes both specs on startup); `foundry openapi --out <path>` writes the **admin** spec only and will not refresh `openapi-wallet.json`.
- Check whether `crates/foundry/AGENTS.md` or `crates/foundry-wallet/AGENTS.md` document the endpoint's body shape; update if so.
